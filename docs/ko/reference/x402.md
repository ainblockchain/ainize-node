# 내 클라이언트로 결제하기

[계정 없이 결제하기](../concepts/payment.md)는 지식을 사는 일이 왜 HTTP 요청 두 번인지를 설명합니다. 이 문서는 그
나머지 절반입니다. Ainize 노드가 **아닌** 클라이언트가 그 두 번의 요청을 성공시키려면 정확히 무엇을 맞춰야 하는지 —
서명하는 대상의 바이트 단위 모양, 게이트웨이가 답하는 모든 상태 코드, 그리고 각 거절이 무슨 뜻인지입니다.

아래 내용은 이 문서를 쓰는 동안 돌아가는 노드에 대고 직접 측정한 것입니다. 코드 블록에 있는 값은 그 실행에서 나온
실제 값이고, 예제는 재현됩니다. 같은 개인키와 같은 견적 항목이면 첫 시도에 같은 해시가 나와야 합니다.

> [!NOTE]
> 노드 하나는 결제 방식을 **하나만** 제시하고, 어느 쪽인지는 그 노드가 쓰는 기록이 정합니다. 로컬 기록을 쓰는 노드는
> `local-credit`과 `CREDIT`을, AIN 체인을 쓰는 노드는 `ain-transfer`와 `AIN`을 제시합니다. `scheme`은 견적에서 읽으세요.
> 짐작하면 안 됩니다.

## 거래를 상태 기계로 보면

```text
GET /x402/patch/<id>                      → 402 + 견적 (nonce, 가격, payTo)
  견적과 내 키로 payload를 만든다
GET /x402/patch/<id>  + X-PAYMENT         → 200 + manifest + 영수증 헤더
                                          → 402 + {"error": …}   결제가 거절됨
  GET <blob_urls[i]>?token=<download_token> → 파일 바이트; sha256 확인
```

두 요청 모두 같은 URL로 갑니다. 세션도, 계정도, 두 번째 엔드포인트도 없습니다.

| 상태 | 언제 | 클라이언트가 할 일 |
|---|---|---|
| `X-PAYMENT` **없는** `402` | 언제나 — 이것은 오류가 아니라 견적 | `x-payment-required`를 읽고, 결제하고, 다시 요청 |
| `200` | 결제가 받아들여짐 | manifest를 받고 파일을 내려받아 sha256 확인 |
| `X-PAYMENT` **있는** `402` | 결제가 거절됨. 이유는 본문에 | [모든 거절 사유](#모든-거절-사유와-그-뜻) 참고 — 대부분은 고칠 수 있고 견적도 살아 있습니다 |
| `404` | 그 id의 지식이 여기 없거나, 아직 비공개 초안 | 다시 시도할 것이 없음 |
| `409` | 이 노드는 그것을 팔지 않음. 메시지가 파는 게이트웨이를 알려 줌 | 그 URL에 대고 처음부터 다시 |
| `410` | 공개한 사람이 내렸음 | 다시 시도하지 말 것 — 영구히 판매 종료 |
| `423` | 아직 목록에 오르지 않았거나(`verification 0/2`), 재검증 요청 중 | 나중에 다시 — 다투는 중에는 어떤 가격도 정직하지 않음 |
| `5xx` | 노드가 고장났거나 앞의 프록시가 고장남 | 간격을 늘려 가며 재시도 |

방금 공개된 지식과, 그것을 팔지 않는 노드에 대고 실제로 측정한 값입니다.

```text
423 {"error":"patch not listed yet (verification 0/2)"}
409 {"error":"not sold here; gateway is http://localhost:3950/x402/patch/x402-doc-check"}
404 {"error":"patch not found"}
```

## 견적

402는 조건을 두 군데에 담아 줍니다. 클라이언트가 이미 보고 있는 곳에서 읽으면 되도록 한 것입니다. 헤더
`x-payment-required`는 JSON 배열의 base64이고, 본문도 같은 배열을 `requirements`와 `accepts` 양쪽에 실어 줍니다.
응답에는 `www-authenticate: x402`도 함께 옵니다.

실제 402에서 나온 조건 하나를 풀면 이렇습니다.

```json
{
  "scheme": "local-credit",
  "network": "local",
  "asset": "CREDIT",
  "payTo": "0x969B880f014eDA7DAcC7a4490F7bCe3484f2BF04",
  "maxAmountRequired": "2",
  "resource": "/x402/patch/x402-doc-check",
  "description": "Knowledge patch x402-doc-check (2992 rows, Qwen3.8-Flash-Next)",
  "nonce": "14dffec7b7d8d2040bcfdb57",
  "expires_at": 1788549193344,
  "requires": [],
  "total": "2",
  "self_contained": true,
  "single_use": true
}
```

| 항목 | 뜻 |
|---|---|
| `scheme` | `local-credit` 또는 `ain-transfer` — 존재하는 방식은 이 둘뿐 |
| `network` | `local` 또는 `ain:local` — 참고용 |
| `asset` | `CREDIT` 또는 `AIN` |
| `payTo` | 판매자 주소. AIN 방식에서는 송금해야 할 곳 |
| `maxAmountRequired` | 가격, 십진 **문자열**. 파싱한 숫자가 아니라 이 문자열을 그대로 서명에 넣을 것 |
| `resource` | 이 견적이 가리키는 경로. 다른 resource로 만든 payload는 거절됨 |
| `description` | 사람이 읽는 문장. 파싱하지 말 것 |
| `nonce` | 이 견적의 신원. 견적 하나에 판매 하나 |
| `expires_at` | epoch 밀리초. 견적은 10분 삽니다 |
| `transfer_key` | `ain-transfer` 전용: 체인 송금이 달고 가야 하는 키 (아래 참고) |
| `requires` | 이 지식이 **밑에** 깔고 있어야 뜻이 통하는 지식들, 각각의 가격과 함께 |
| `total` | 이 지식과 `requires` 전부를 더한 정가 |
| `self_contained` | `requires`가 비어 있으면 `true` |
| `single_use` | 이 nonce로는 두 번째 판매가 일어나지 않음 |

> [!IMPORTANT]
> 클라이언트가 가장 많이 놓치는 것이 `requires`입니다. 다른 지식 위에 얹어 학습한 지식은 그 밑바탕 없이는 아무것도
> 하지 않으므로, `maxAmountRequired`만 내고 끝낸 구매자는 쓸 수 없는 파일을 산 것입니다. 밑바탕까지 사거나,
> `self_contained`가 `true`인 지식을 고르세요.
>
> ainize 노드에서는 가족 전체가 한 번의 호출입니다. `POST /api/patches/<id>/buy?bundle=1`은 `requires`에 있는 것들을
> 깊은 것부터 먼저 사고 — 각각 결제 한 번, 정산 기록 한 건 — `purchases[]`를 그 순서로, 실제로 나간 합계를 `total`로
> 돌려줍니다(`ainize patch buy <id> --bundle`). 적재도 같은 규칙입니다. `POST /api/patches/<id>/apply
> {"with_base": true}`는 밑바탕을 먼저 쓰고 추가분을 올린 뒤, 사용한 `order`를 함께 답합니다. 설계는
> `docs/lineage-teach-design.md` §8.7, §12.4.

## `local-credit`: 의사, 해시, 서명

로컬 기록에는 옮길 것이 없습니다. 정산 기록을 쓰는 것이 곧 결제입니다. 그래서 보내는 것은 서명된 의사 표시입니다.
세 단계이고, 셋 다 판매자와 바이트 단위로 같아야 합니다.

**1. 의사를 만든다.** 정확히 이 다섯 항목, 그 밖의 것은 넣지 않습니다.

| 키 | 값 |
|---|---|
| `resource` | 견적의 `resource` |
| `amount` | 견적의 `maxAmountRequired`를 받은 문자열 그대로 |
| `nonce` | 견적의 `nonce` |
| `payTo` | 견적의 `payTo` |
| `from` | 내 주소 |

**2. 정규화해서 직렬화하고 해시한다.** 정규화란, 공백 없는 압축 JSON(`:`이나 `,` 뒤에 공백을 두지 않습니다)에 모든
객체의 키를 모든 깊이에서 정렬한 것입니다. 여기서 정렬된 순서는 위 표의 순서가 아니라
`amount, from, nonce, payTo, resource`입니다. 이것을 틀리는 것이 `invalid payment signature`의 가장 흔한 원인입니다.
순서가 다르면 그냥 다른 해시가 되기 때문입니다.

```text
{"amount":"2","from":"0xFCAd0B19bB29D4674531d6f115237E16AfCE377c","nonce":"14dffec7b7d8d2040bcfdb57","payTo":"0x969B880f014eDA7DAcC7a4490F7bCe3484f2BF04","resource":"/x402/patch/x402-doc-check"}
```

의사 해시는 **그 문자열의 sha256 16진수**입니다. 소문자, `0x` 없이.

```text
2de6d2aa7d93f3e6a5aa6e6ecc98c9ef94f26c9c3d6a6556408ccd54c418960c
```

이 해시가 서명 대상이면서 동시에 `txHash`에 넣는 값입니다. 이 방식에서는 의사 해시가 곧 거래 id이고,
`x-payment-tx-hash`로 돌아오며 공개 기록에도 그대로 남습니다.

**3. 해시 문자열에 서명한다.** 서명은 그 64자 16진수 **문자열**에 대한 AI Network 서명 메시지입니다. 문자열이
가리키는 바이트가 아닙니다. `ain-util`의 `ecSignMessage`가 한 번에 해 주고, 어느 언어로도 그대로 재현할 수 있습니다.

- `hashed = keccak256(keccak256(varuint(26) ‖ "AINetwork Signed Message:\n" ‖ varuint(len(msg)) ‖ msg))` —
  `varuint`는 비트코인의 가변 길이 정수 인코딩이고, 우리 16진수 문자열에서 `len(msg)`는 64입니다
- `hashed`를 secp256k1로, 복구 가능하게 서명합니다
- 서명 문자열은 `0x` 뒤에 `hashed`(32바이트) ‖ `r`(32) ‖ `s`(32) ‖ `v`(1, `recovery + 27`)를 이어 붙인 것으로,
  전부 196자입니다

판매자는 이 서명에서 주소를 복구해 `from`과 비교합니다. 다른 키로 서명하면 나머지가 모두 맞아도 실패합니다.

## `ain-transfer`: 송금, 키, 증명

AIN 기록을 쓰는 노드에서는 돈이 먼저 실제로 움직이고, payload는 그 송금이 내 것이며 **이 견적**에 대한 것임을
증명합니다.

- `payTo`로 최소 `maxAmountRequired`만큼, **견적의 transfer key를 달고** 송금합니다. 키는
  `x402_<nonce>_<resource에서 A-Z a-z 0-9 _ - 이외의 문자를 _로 바꾼 뒤 뒤에서 40자>` 형태입니다. 예를 들어
  `x402_7af713ed70d8d680059d79a1__x402_patch_capital-facts`. 다른 키를 단 송금은 이유 없이 도착한 돈이고, 아무것도
  사지 못합니다.
- `sha256("x402-ain:" ‖ txHash ‖ ":" ‖ nonce)` 다이제스트를 **송금한** 키로, 위와 같은 방식으로 서명합니다. 공개
  체인의 거래 해시는 소지자 증표가 아닙니다. 체인을 먼저 읽은 사람이 파일을 가져가는 일을 막는 것이 이 서명입니다.
- payload에 `txHash`, `nonce`, 그 서명을 `proof`로 넣습니다.

판매자는 체인에서 그 거래를 찾아보며 몇 초 동안 재시도합니다. 방금 송금을 받아들인 체인이 언제나 즉시 그것을 보여
주지는 않기 때문입니다.

## payload

아래 JSON을 base64로 만들어 `X-PAYMENT` 헤더에 담습니다. 여기서는 키 순서가 상관없습니다. 순서가 중요한 것은
의사(intent)뿐입니다.

| 항목 | `local-credit` | `ain-transfer` |
|---|---|---|
| `scheme` | `"local-credit"` | `"ain-transfer"` |
| `network`, `asset` | 견적에서 복사 | 견적에서 복사 |
| `amount` | 견적의 `maxAmountRequired` | 견적의 `maxAmountRequired` |
| `nonce` | 견적의 `nonce` | 견적의 `nonce` |
| `from` | 내 주소 | 무시됨 — 지불자는 송금에서 읽음 |
| `payTo` | 견적의 `payTo` | 견적의 `payTo` |
| `txHash` | 의사 해시 | 체인의 거래 해시 |
| `proof` | 의사 해시에 대한 서명 | `sha256("x402-ain:<txHash>:<nonce>")`에 대한 서명 |

## 200이 주는 것

```text
x-payment-tx-hash : 2de6d2aa7d93f3e6a5aa6e6ecc98c9ef94f26c9c3d6a6556408ccd54c418960c
x-payment-currency: CREDIT
x-payment-response: {"settled":true,"tx":"2de6d2aa…","royalty":{"0x13eBbd33…":"0.05","0xDe7DeAa2…":"0.05","0x969B880f…":"1.9"}}
x-content-sha256  : <본문(manifest)의 sha256>
```

`x-payment-response`가 영수증입니다. `settled`, 거래 id, 그리고 분배 전체 — 내 돈에서 누구에게 얼마가 갔는지가 모두
들어 있습니다. 위 실행에서는 2 CREDIT으로 지식을 샀고, 그것을 검증한 노드 둘에게 각각 0.05가 갔으며, 나머지가
판매자에게 갔습니다. 같은 결제를 다시 냈을 때는 `replayed: true`와 `settled_at`이 더 붙습니다.

본문은 [`Manifest`](./schemas.md#manifest)이고, 지식 파일 자체가 **아닙니다**.

```json
{
  "id": "x402-doc-check",
  "patch_sha256": "62d0978ccbf0b31083c77b836f16c5a2ef795cfade5eebebea1ebc6931aace26",
  "size_bytes": 3854446,
  "rows": 2992,
  "model": { "row_dim": 160, "id_M": "Qwen3.8-Flash-Next" },
  "benchmark_hash": "0d2408a813c79b89149ca59f4c6473a991eac94691e64bf44277992af71b8488",
  "blob_urls": ["http://localhost:3950/p2p/blob/62d0978c…", "http://localhost:3952/p2p/blob/62d0978c…"],
  "issued_to": "0xFCAd0B19bB29D4674531d6f115237E16AfCE377c",
  "issued_at": 1788548593407,
  "download_token": "dde4bad6…"
}
```

파일은 `blob_urls`의 **아무** 주소에서나 `GET <blob_url>?token=<download_token>`으로 받으면 됩니다. 판매자가 아닌
경우가 오히려 흔합니다. 받은 바이트의 sha256을 `patch_sha256`과 맞춰 보세요. 그 값은 돈을 내기 전부터 공개 기록에
있던 값입니다. 이 확인이 내려받기의 보안 전부이고, 그래서 누가 바이트를 보내 줬는지는 중요하지 않습니다.

토큰은 24시간 유효하며 그 파일과 나에게 묶여 있습니다. `blob_urls`는 오래되면 죽을 수 있으니(가지고 있던 노드가
내려가면) 다음 것을 시도하세요.

## 재시도, 재제출, 그리고 두 번 내는 일

- **같은 결제를 다시 내는 것은 안전합니다.** 판매자는 새 manifest와 `replayed: true`로 `200`을 답하고, 아무것도
  더 청구하지 않습니다. 응답을 잃어버렸을 때의 올바른 복구 방법이고, 위에서 측정한 그대로입니다.
- **남의 결제를 대신 내미는 것은 거절됩니다.** `payment already used`가 돌아옵니다. 다시 받으려면 지불한 주소의
  서명이 필요합니다.
- **거절된 시도는 견적을 태우지 않습니다.** nonce는 금액·서명·잔액을 모두 확인한 뒤 맨 마지막에 소비되므로,
  `amount below price`나 `invalid payment signature`가 나도 nonce는 그대로 살아 있고 같은 견적으로 다시 내면
  성공합니다. 측정: `0.5`짜리 시도가 거절된 뒤, 같은 nonce의 올바른 payload가 그대로 받아들여졌습니다.
- **판매가 끝나면 nonce는 소비됩니다.** 모두에게 그렇습니다. 그 nonce를 들고 온 다른 지불자에게는 그렇다고 이름을
  들어 알려 줍니다.
- anchor의 `billing: per_download`는 말 그대로입니다. 새 견적과 새 결제는 새 판매입니다. 좌석도, 구독도 없고,
  위의 재제출과 24시간 토큰 말고 포함된 재다운로드도 없습니다.

## 모든 거절 사유와 그 뜻

전부 `402`에 `{"error": …}`로 돌아옵니다. 측정한 문장 그대로입니다.

| 메시지 | 원인 | 할 일 |
|---|---|---|
| `missing or malformed X-PAYMENT` | 헤더가 JSON 객체의 base64가 아님 | 인코딩을 고칠 것 |
| `unsupported scheme <x>` | `scheme`이 없거나 둘 중 하나가 아님 | 견적의 `scheme`을 복사할 것 |
| `local-credit payload needs nonce, from, proof` | 필수 항목이 빠짐 | — |
| `this node does not sell that patch` | 노드를 잘못 찾아감 | `409`가 알려 준 게이트웨이로 |
| `unknown or expired nonce` | 여기서 발급한 적 없거나, 10분이 지났거나, 다른 resource의 것 | 다시 GET해서 새 견적을 받을 것 |
| `nonce <n> was consumed by an earlier attempt` | 이 견적으로 이미 결제가 성사됨 | 다시 GET해서 새 견적을 받을 것 |
| `amount below price` | `amount`가 가격보다 적음 | `maxAmountRequired`를 보낼 것 |
| `invalid payment signature` | 복구한 주소가 `from`이 아님 — 보통 정규화가 틀린 경우 | 키 순서와 공백 없는 JSON을 다시 확인할 것 |
| `insufficient credit: <bal> < <price>` | 로컬 크레딧 잔액이 모자람. 이 노드가 아직 시작 크레딧을 주는지도 함께 알려 줌 | 운영자에게 요청하거나, 무언가를 팔 것 |
| `payment already used` | 이미 정산된 거래인데 정산한 지불자가 내가 아님 | — |
| `transfer not found / not executed` | 체인에 그 거래가 (아직) 없음 | 기다렸다 다시 시도할 것 |
| `transfer recipient <a> is not the seller` | 다른 주소로 보냄 | `payTo`로 보낼 것 |
| `transfer <t> below price <p>` | 적게 보냄 | — |
| `ain-transfer payload needs the nonce from the 402` | payload에 `nonce`가 없음 | — |
| `transfer <t> was not made against this quote` | 송금 키가 `transfer_key`가 아님 | 그 키를 달고 다시 송금할 것 |
| `payment proof is not signed by the payer` | `proof` 서명에서 송금한 주소가 복구되지 않음 | 송금한 키로 서명할 것 |

## 완성된 클라이언트

Node로 쓴 것이고, 이 저장소의 코드는 하나도 쓰지 않습니다. `fetch`, `node:crypto`, 그리고 서명을 위한
`@ainblockchain/ain-util`뿐입니다. 나머지는 전부 위의 규격입니다.

```js
import { createHash } from 'node:crypto';
import ainUtil from '@ainblockchain/ain-util';

const NODE = 'http://localhost:3950';
const RESOURCE = '/x402/patch/x402-doc-check';
const PRIV = '…16진수 64자…';
const from = ainUtil.privateToAccount(Buffer.from(PRIV, 'hex')).address;

// 모든 깊이에서 키를 정렬한, 공백 없는 JSON
const canonical = (v) => JSON.stringify(v, (_, x) =>
  (x && typeof x === 'object' && !Array.isArray(x))
    ? Object.fromEntries(Object.keys(x).sort().map((k) => [k, x[k]]))
    : x);

const r1 = await fetch(NODE + RESOURCE);
const [req] = JSON.parse(Buffer.from(r1.headers.get('x-payment-required'), 'base64').toString('utf8'));

const intent = { resource: req.resource, amount: req.maxAmountRequired, nonce: req.nonce, payTo: req.payTo, from };
const txHash = createHash('sha256').update(canonical(intent)).digest('hex');
const proof = ainUtil.ecSignMessage(txHash, Buffer.from(PRIV, 'hex'));

const payload = { scheme: req.scheme, network: req.network, asset: req.asset,
  amount: req.maxAmountRequired, nonce: req.nonce, from, payTo: req.payTo, txHash, proof };
const r2 = await fetch(NODE + RESOURCE, {
  headers: { 'X-PAYMENT': Buffer.from(JSON.stringify(payload)).toString('base64') } });
if (r2.status !== 200) throw new Error(`payment refused: ${await r2.text()}`);
const manifest = await r2.json();

const bytes = Buffer.from(await (await fetch(`${manifest.blob_urls[0]}?token=${manifest.download_token}`)).arrayBuffer());
if (createHash('sha256').update(bytes).digest('hex') !== manifest.patch_sha256) throw new Error('body does not match the record');
```

다른 언어에서도 표준 라이브러리 밖에 있는 것은 서명 하나뿐입니다. 정규화 JSON, sha256, base64, GET 두 번은 이미 다
가지고 있습니다.

## 이것을 쓰기 전에

`ainize use <id>` 한 줄이 이 거래 전체를 합니다. [에이전트](./cli.md)는 사람 없이 같은 일을 합니다. 이 문서대로
구현할 이유는 내 클라이언트가 Ainize 노드일 수 없을 때입니다. 파이썬 서비스, Go 에이전트, 이미 키를 쥐고 있는 지갑
같은 경우입니다. 노드일 수 있다면 CLI로 사고, 시간은 그 지식으로 무엇을 할지에 쓰세요.

함께 읽기: 생성된 스키마 레퍼런스의 [`X402Requirement`](./schemas.md#x402requirement)와
[`X402Payload`](./schemas.md#x402payload), HTTP API의
[`GET /x402/patch/{id}`](./http-api.md#get-x402patchid), 그리고 이 거래가 부호가 아니라 무엇을 뜻하는지는
[계정 없이 결제하기](../concepts/payment.md).
