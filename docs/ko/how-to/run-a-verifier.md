# 검증에 드는 비용

`ainize init`은 새 노드에 역할 셋을 주고 한 줄로 알려 줍니다.

```text
roles    seller, verifier, serving
```

가운데 있는 `verifier`가, 내 기계를 남을 위해 일하게 만드는 유일한 역할입니다. 아무런 경고가 없는 이유는, 이
네트워크에서 검증이 호의가 아니기 때문입니다. 공개한 사람이 아닌 다른 노드 두 곳이 확인해 주기 전에는 어떤 지식도
어디서도 목록에 오르지 않습니다. 내 노드가 남의 지식을 검사하는 것은, 그것이 내 지식도 검사받는 유일한 길이기
때문입니다.

여기까지가 검증을 켜 두는 이유입니다. 이 문서는 청구서 쪽입니다.

## 묻지 않고 하는 일

`roles`에 `verifier`가 있고 [`verifier.auto`](../reference/config.md#keys)가 기본값 `true`이면, 노드는 5초마다 검증
한 바퀴를 돕니다. 한 바퀴마다 아직 검증하지 않은 공개된 지식을 찾아 **파일 전체를 내려받고**, 공개 기록의 anchor에
적힌 sha256과 맞는지 확인합니다. 그리고 그 노드가 맞는 모델까지 서비스하고 있다면, 지식을 모델에 넣고 벤치마크
질문을 던지고 답을 채점한 뒤 원래대로 되돌리고, 서명한 [검증 기록](../concepts/verification.md)을 남깁니다.

이 문서를 쓰면서 검증 노드 두 대짜리 새 네트워크에서 지식 두 개를 검증해 봤습니다. 아무것도 공개하지 않았고 아무것도
사지 않은 노드의 디스크는 이렇게 되어 있었습니다.

```text
Disk used  351,683,460 bytes in 2 files — all of it reclaimable
```

그중 자기 것은 하나도 없습니다. 두 파일 중 하나는 348 MB인데, 그 지식이 원래 그만큼이기 때문입니다. 사람이 붐비는
네트워크에서 일주일을 돈 노드라면, 쓸 일이 없는 파일 수백 개를 안고 있게 됩니다.

## 드는 것 세 가지

**디스크.** 검증한 것의 파일이 그대로 남습니다. `ainize gc --dry-run`은 정리하면 얼마가 비는지 알려 주고,
`ainize gc`가 실제로 지웁니다. `--older-than 30d`를 붙이면 최근 사본은 남기니, 재검증 요청으로 같은 파일이 다시
돌아올 때 대비가 됩니다. 지운 사본은 필요하면 다시 받아 오므로 망가지는 것은 없습니다. 디스크를 대역폭과 바꾸는
셈입니다.

**내 모델.** 노드에 `serving` 역할이 있으면, 벤치마크를 도는 동안 공유 런타임 잠금(`verify:<id>`라는 이름이
붙습니다)을 잡고 나머지가 전부 그 뒤에 줄을 섭니다. 내 방문자의 라이브 테스트도, 내 `ainize chat`도, 내가 지식을
넣고 빼는 일도 마찬가지입니다. 한 기계 위의 여러 노드는 이 잠금을 함께 쓰므로, 데모 노드 셋은 줄 하나입니다. 죽은
채로 잠금을 쥐고 있는 경우는 15분이 지나면 풀립니다.

**책임.** 검증 노드는 공개 기록의 당사자입니다. 검증 기록은 노드의 키로 서명되어 영구히 남고, 사는 사람이 돈을 쓰기
전에 읽는 바로 그 숫자가 됩니다. 잘못 쓴 것을 되돌릴 방법은 없습니다.

## 받는 것

`market.verifierShare`는 바꾸지 않았다면 `0.05`이고, **판매 한 건마다** 그 비율이 검증으로 인정된 노드들에게 나뉘어
갑니다. 판매자 몫에서 빠져나가며, 판매가 일어나는 그 순간 정산 기록에 함께 적힙니다.

같은 네트워크에서, 지식 하나를 검증했고 그것이 세 번 팔린 노드의 지갑입니다.

```text
earned from verifying  0.15 CREDIT over 3 sale(s) of knowledge you verified
```

이 줄은 `ainize wallet`에 있고, 웹 화면에서는 계정 설정에 같은 내용이 있습니다. 수입을 계획에 넣기 전에 알아 둘 것이
둘 있습니다.

- **팔리지 않는 지식을 검증한 값은 아무도 주지 않습니다.** 그리고 대부분의 지식은 팔리지 않습니다. 디스크 비용은
  확실하고, 수입은 그렇지 않습니다.
- **무결성만 확인한 검증도 인정되기만 하면 실제로 실행한 검증과 똑같이 받습니다.** 인정 여부를 가르는 것은 내 노드가
  얼마나 일했는지가 아니라 [그 지식이 벤치마크 질문을 내걸었는지](../concepts/verification.md)입니다.

## 끄는 법

스위치는 둘이고, 둘 다 노드를 다시 띄워야 적용됩니다.

```bash
# 배경에서 도는 검증을 멈춘다. 요청받으면 여전히 검증한다 (ainize patch verify)
ainize config set verifier.auto false

# 아니면 역할 자체를 뺀다
ainize config set roles seller,serving
```

둘 다 같은 경고를 함께 찍습니다. 여기 옮겨 둘 만한 문장입니다.

```text
! the node … is running on http://localhost:3951 and keeps using the value it started with —
  restart it to apply this (`ainize stop` then `ainize start -d`)
```

그다음, 이미 쓴 자리를 되찾습니다.

```bash
ainize gc --dry-run
ainize gc
```

> [!IMPORTANT]
> 모두가 이것을 끄는 네트워크는 아무것도 공개하지 못합니다. 정족수는 글쓴이가 아닌 노드 두 곳의 검증이므로, 무언가를
> 목록에 올릴 수 있는 가장 작은 네트워크는 참가자 셋입니다. 노드 셋짜리 개인 네트워크에서 둘의 `verifier`를 꺼 두면
> 공개하는 것마다 영원히 `0/2`에 머무릅니다. 버그처럼 보이지만 버그가 아닙니다.

## 켜 둔 채로 지낸다면

- 채워도 아깝지 않은 디스크를 주고, `ainize gc --older-than 30d`를 주 1회 타이머에 걸어 두세요.
- 사람들이 쓰는 모델을 같이 서비스하는 노드라면, 벤치마크가 도는 동안 모델이 멈추는 것을 감수해야 합니다. 모델이 없는
  검증 노드도 쓸모가 있습니다. 무결성을 확인해 주고, 벤치마크 질문을 내걸지 않은 지식은 그것만으로 목록에 오릅니다.
- `ainize logs`에서 `verify` 이벤트를 지켜보세요. 판매자 노드에 닿지 못했거나 그 지식의 `id_M`에 맞는 모델이 없으면,
  조용히 실패하는 대신 그 자리에 이유가 적힙니다.

함께 읽기: 내 검증 기록이 사는 사람에게 어떤 값인지는 [검증 완료가 증명하는 것](../concepts/verification.md), 같은
장치의 반대편은 [목록에 오르지 않을 때](./failed-verification.md).
