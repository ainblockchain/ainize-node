# Paying from your own client

[Paying without an account](../concepts/payment.md) explains why buying knowledge is two HTTP requests. This page is
the other half: everything a client that is **not** an Ainize node has to get exactly right to make those two
requests work — the byte-for-byte shape of what you sign, every status code the gateway answers with, and what each
refusal means.

Everything below was measured against a running node while this page was written. Where a value appears in a code
block it is a real value from that run, and the worked example is reproducible: the same private key and the same
quote fields must give you the same hash on the first try.

> [!NOTE]
> A node offers exactly **one** scheme, and the ledger it runs decides which: a node on the local ledger quotes
> `local-credit` and `CREDIT`, a node on the AIN chain quotes `ain-transfer` and `AIN`. Read `scheme` out of the
> quote; never assume it.

## The exchange, as a state machine

```text
GET /x402/patch/<id>                      → 402 + quote  (nonce, price, payTo)
  build payload from the quote and your key
GET /x402/patch/<id>  with X-PAYMENT      → 200 + manifest + receipt headers
                                          → 402 + {"error": …}   the payment was refused
  GET <blob_urls[i]>?token=<download_token> → the bytes; check sha256
```

Both requests go to the same URL. There is no session, no account and no second endpoint.

| Status | When | What a client should do |
|---|---|---|
| `402` **without** `X-PAYMENT` | always — this is the quote, not an error | read `x-payment-required`, pay, ask again |
| `200` | the payment was accepted | take the manifest, download the body, check its sha256 |
| `402` **with** `X-PAYMENT` | the payment was refused; the body says why | see [every refusal](#every-refusal-and-what-it-means) — most are fixable and keep your quote |
| `404` | no knowledge with that id here, or it is still a private draft | nothing to retry |
| `409` | this node does not sell it; the message names the gateway that does | repeat the whole exchange against that URL |
| `410` | the publisher retired it | never retry — it is off sale for good |
| `423` | not listed yet (`verification 0/2`), or a verifier has challenged it | retry later; no price is honest while it is disputed |
| `5xx` | the node is broken, or a proxy in front of it is | retry with backoff |

Measured, on a knowledge announced seconds earlier and on a node that does not sell it:

```text
423 {"error":"patch not listed yet (verification 0/2)"}
409 {"error":"not sold here; gateway is http://localhost:3950/x402/patch/x402-doc-check"}
404 {"error":"patch not found"}
```

## The quote

The 402 carries the terms twice, so a client can read them from wherever it already looks: the header
`x-payment-required` is base64 of a JSON array, and the body repeats that array under both `requirements` and
`accepts`. The response also carries `www-authenticate: x402`.

One requirement, decoded, from a real 402:

```json
{
  "scheme": "local-credit",
  "network": "local",
  "asset": "CREDIT",
  "payTo": "0x969B880f014eDA7DAcC7a4490F7bCe3484f2BF04",
  "maxAmountRequired": "2",
  "resource": "/x402/patch/x402-doc-check",
  "description": "Knowledge patch x402-doc-check (2992 rows, Qwen3.8-Flash-Next)",
  "nonce": "14dffec7b7d8d2040bcfdb57",
  "expires_at": 1788549193344,
  "requires": [],
  "total": "2",
  "self_contained": true,
  "single_use": true
}
```

| Field | What it is |
|---|---|
| `scheme` | `local-credit` or `ain-transfer` — the only two that exist |
| `network` | `local` or `ain:local` — informational |
| `asset` | `CREDIT` or `AIN` |
| `payTo` | the seller's address: on the AIN path, where the transfer must go |
| `maxAmountRequired` | the price, as a decimal **string**. Sign this string, not a number you parsed out of it |
| `resource` | the path this quote is for. A payload built for another resource is refused |
| `description` | human text; never parse it |
| `nonce` | the quote's identity. One quote, one sale |
| `expires_at` | epoch ms; the quote lives 10 minutes |
| `transfer_key` | `ain-transfer` only: the key the on-chain transfer must carry (see below) |
| `requires` | the knowledge this one has to be loaded **under** to mean anything, each with its own price |
| `total` | the family's list price: this knowledge plus every entry in `requires` |
| `self_contained` | `true` when `requires` is empty |
| `single_use` | the nonce cannot be used for a second sale |

> [!IMPORTANT]
> `requires` is the part most clients miss. A knowledge trained on top of another does nothing without it, so a buyer
> that pays `maxAmountRequired` and stops has bought a file it cannot use. Buy the bases too, or pick a knowledge
> whose `self_contained` is `true`.
>
> On an ainize node the whole family is one call: `POST /api/patches/<id>/buy?bundle=1` buys the entries of
> `requires` first, deepest first, one payment and one settlement record each, and answers with `purchases[]` in
> that order and the `total` that actually moved (`ainize patch buy <id> --bundle`). Loading follows the same rule:
> `POST /api/patches/<id>/apply {"with_base": true}` writes the bases underneath before the add-on and answers with
> the `order` it used. Design: `docs/lineage-teach-design.md` §8.7, §12.4.

## `local-credit`: the intent, the hash, the signature

There is nothing to transfer on the local ledger — writing the settlement **is** the payment — so what you send is a
signed statement of intent. Three steps, and every one of them has to match the seller byte for byte.

**1. Build the intent.** Exactly these five fields, no others:

| Key | Value |
|---|---|
| `resource` | `resource` from the quote |
| `amount` | `maxAmountRequired` from the quote, as the string it was given as |
| `nonce` | `nonce` from the quote |
| `payTo` | `payTo` from the quote |
| `from` | your own address |

**2. Serialise it canonically and hash it.** Canonical means: compact JSON — no spaces after `:` or `,` — with the
keys of every object sorted, at every depth. The sorted order here is not the order above; it is
`amount, from, nonce, payTo, resource`. Getting that wrong is the single most common cause of
`invalid payment signature`, because your hash is then simply a different hash.

```text
{"amount":"2","from":"0xFCAd0B19bB29D4674531d6f115237E16AfCE377c","nonce":"14dffec7b7d8d2040bcfdb57","payTo":"0x969B880f014eDA7DAcC7a4490F7bCe3484f2BF04","resource":"/x402/patch/x402-doc-check"}
```

The intent hash is the **hex sha256 of that string**, lower case, no `0x`:

```text
2de6d2aa7d93f3e6a5aa6e6ecc98c9ef94f26c9c3d6a6556408ccd54c418960c
```

That hash is both what you sign **and** what you put in `txHash`: on this scheme the intent hash is the transaction
id, and it is what comes back in `x-payment-tx-hash` and goes on the public record.

**3. Sign the hash string.** The signature is an AI Network signed message over the 64-character hex string — not
over the bytes it encodes. `ain-util`'s `ecSignMessage` does it in one call, and any language can reproduce it:

- `hashed = keccak256(keccak256(varuint(26) ‖ "AINetwork Signed Message:\n" ‖ varuint(len(msg)) ‖ msg))`, where
  `varuint` is Bitcoin's variable-length integer encoding and `len(msg)` is 64 for our hex string
- sign `hashed` with secp256k1, recoverable
- the signature string is `0x` followed by `hashed` (32 bytes) ‖ `r` (32) ‖ `s` (32) ‖ `v` (1, which is
  `recovery + 27`) — 196 characters in all

The seller recovers your address from it and compares it with `from`, so a signature by any other key fails even
when every other field is right.

## `ain-transfer`: the transfer, the key, the proof

On a node running the AIN ledger the money really moves first, and the payload proves the transfer was yours and was
made against **this** quote.

- Transfer at least `maxAmountRequired` to `payTo` **with the transfer key from the quote**. The key is
  `x402_<nonce>_<resource with every character outside A-Z a-z 0-9 _ - replaced by _, last 40 characters>` — e.g.
  `x402_7af713ed70d8d680059d79a1__x402_patch_capital-facts`. A transfer that carries any other key is money that
  arrived for no particular reason: it buys nothing.
- Sign the digest `sha256("x402-ain:" ‖ txHash ‖ ":" ‖ nonce)` with the **paying** key, the same way as above. A
  transaction hash on a public chain is not a bearer ticket, and this is what stops whoever reads the chain first
  from collecting the file.
- Put `txHash`, `nonce` and that signature in `proof`.

The seller looks the transaction up on chain, retrying for a few seconds — a chain that has just accepted a transfer
does not always report it instantly.

## The payload

Base64 of the JSON below, in the `X-PAYMENT` header. Key order does not matter here; only the intent's does.

| Field | `local-credit` | `ain-transfer` |
|---|---|---|
| `scheme` | `"local-credit"` | `"ain-transfer"` |
| `network`, `asset` | copied from the quote | copied from the quote |
| `amount` | the quote's `maxAmountRequired` | the quote's `maxAmountRequired` |
| `nonce` | the quote's `nonce` | the quote's `nonce` |
| `from` | your address | ignored — the payer is read off the transfer |
| `payTo` | the quote's `payTo` | the quote's `payTo` |
| `txHash` | the intent hash | the on-chain transaction hash |
| `proof` | signature over the intent hash | signature over `sha256("x402-ain:<txHash>:<nonce>")` |

## What 200 gives you

```text
x-payment-tx-hash : 2de6d2aa7d93f3e6a5aa6e6ecc98c9ef94f26c9c3d6a6556408ccd54c418960c
x-payment-currency: CREDIT
x-payment-response: {"settled":true,"tx":"2de6d2aa…","royalty":{"0x13eBbd33…":"0.05","0xDe7DeAa2…":"0.05","0x969B880f…":"1.9"}}
x-content-sha256  : <sha256 of the body, which is the manifest>
```

`x-payment-response` is the receipt: `settled`, the transaction id, and the whole split — every address that was
paid out of your money and how much. In the run above, 2 CREDIT bought the knowledge and paid 0.05 to each of the
two nodes that verified it; the rest went to the seller. On a replay it also carries `replayed: true` and
`settled_at`.

The body is the [`Manifest`](./schemas.md#manifest) — **not** the knowledge file:

```json
{
  "id": "x402-doc-check",
  "patch_sha256": "62d0978ccbf0b31083c77b836f16c5a2ef795cfade5eebebea1ebc6931aace26",
  "size_bytes": 3854446,
  "rows": 2992,
  "model": { "row_dim": 160, "id_M": "Qwen3.8-Flash-Next" },
  "benchmark_hash": "0d2408a813c79b89149ca59f4c6473a991eac94691e64bf44277992af71b8488",
  "blob_urls": ["http://localhost:3950/p2p/blob/62d0978c…", "http://localhost:3952/p2p/blob/62d0978c…"],
  "issued_to": "0xFCAd0B19bB29D4674531d6f115237E16AfCE377c",
  "issued_at": 1788548593407,
  "download_token": "dde4bad6…"
}
```

Fetch the bytes from **any** URL in `blob_urls` — often not the seller — as
`GET <blob_url>?token=<download_token>`, and check their sha256 against `patch_sha256`, which was on the public
record before you paid. That check is the whole security model of the download: it does not matter who served the
bytes.

The token is good for 24 hours and is bound to that body and to you. `blob_urls` can go stale (a holder goes
offline); try the next one.

## Retrying, replaying, and paying twice

- **Presenting the same payment again is safe.** The seller answers `200` with a fresh manifest, `replayed: true`,
  and charges nothing. This is the right way to recover a lost response — measured above.
- **A stranger presenting your payment is refused** with `payment already used`: re-issue requires the signature of
  the address that paid.
- **A refused attempt does not burn your quote.** The nonce is spent last, after the amount, the signature and the
  balance have all been checked, so `amount below price` and `invalid payment signature` leave the nonce usable and
  the correct retry succeeds against the same quote. Measured: a `0.5` attempt was refused, and the correct payload
  with the same nonce was then accepted.
- **A completed sale does consume the nonce**, for everyone. Another payer arriving with it is told so by name.
- `billing: per_download` on an anchor means what it says: a new quote and a new payment is a new sale. There is no
  seat, no subscription and no included re-download beyond the replay above and the 24-hour token.

## Every refusal, and what it means

All of these come back as `402` with `{"error": …}` — measured, verbatim:

| Message | Cause | What to do |
|---|---|---|
| `missing or malformed X-PAYMENT` | the header is not base64 of a JSON object | fix the encoding |
| `unsupported scheme <x>` | `scheme` is absent or is not one of the two | copy `scheme` from the quote |
| `local-credit payload needs nonce, from, proof` | a required field is missing | — |
| `this node does not sell that patch` | you are asking the wrong node | use the gateway named in the `409` |
| `unknown or expired nonce` | the nonce was never issued here, is over 10 minutes old, or belongs to another resource | GET again for a new quote |
| `nonce <n> was consumed by an earlier attempt` | somebody's payment against this quote already settled | GET again for a new quote |
| `amount below price` | `amount` is less than the price | send `maxAmountRequired` |
| `invalid payment signature` | the recovered address is not `from` — usually a non-canonical intent | re-check the key order and the compact JSON |
| `insufficient credit: <bal> < <price>` | your local-credit balance does not cover it, and the message says whether this node still issues starting credit | ask the operator, or sell something |
| `payment already used` | this transaction is settled and you are not the payer that settled it | — |
| `transfer not found / not executed` | the chain does not have that transaction (yet) | wait for it, then retry |
| `transfer recipient <a> is not the seller` | you paid the wrong address | transfer to `payTo` |
| `transfer <t> below price <p>` | you paid too little | — |
| `ain-transfer payload needs the nonce from the 402` | no `nonce` in the payload | — |
| `transfer <t> was not made against this quote` | the transfer's key is not `transfer_key` | transfer again with that key |
| `payment proof is not signed by the payer` | the `proof` signature does not recover the transferring address | sign with the paying key |

## A complete client

Node, using nothing from this repository — `fetch`, `node:crypto` and `@ainblockchain/ain-util` for the signature.
Everything else is the protocol above.

```js
import { createHash } from 'node:crypto';
import ainUtil from '@ainblockchain/ain-util';

const NODE = 'http://localhost:3950';
const RESOURCE = '/x402/patch/x402-doc-check';
const PRIV = '…64 hex characters…';
const from = ainUtil.privateToAccount(Buffer.from(PRIV, 'hex')).address;

// compact JSON with every key sorted, at every depth
const canonical = (v) => JSON.stringify(v, (_, x) =>
  (x && typeof x === 'object' && !Array.isArray(x))
    ? Object.fromEntries(Object.keys(x).sort().map((k) => [k, x[k]]))
    : x);

const r1 = await fetch(NODE + RESOURCE);
const [req] = JSON.parse(Buffer.from(r1.headers.get('x-payment-required'), 'base64').toString('utf8'));

const intent = { resource: req.resource, amount: req.maxAmountRequired, nonce: req.nonce, payTo: req.payTo, from };
const txHash = createHash('sha256').update(canonical(intent)).digest('hex');
const proof = ainUtil.ecSignMessage(txHash, Buffer.from(PRIV, 'hex'));

const payload = { scheme: req.scheme, network: req.network, asset: req.asset,
  amount: req.maxAmountRequired, nonce: req.nonce, from, payTo: req.payTo, txHash, proof };
const r2 = await fetch(NODE + RESOURCE, {
  headers: { 'X-PAYMENT': Buffer.from(JSON.stringify(payload)).toString('base64') } });
if (r2.status !== 200) throw new Error(`payment refused: ${await r2.text()}`);
const manifest = await r2.json();

const bytes = Buffer.from(await (await fetch(`${manifest.blob_urls[0]}?token=${manifest.download_token}`)).arrayBuffer());
if (createHash('sha256').update(bytes).digest('hex') !== manifest.patch_sha256) throw new Error('body does not match the record');
```

In another language the only piece that is not standard library is the signature. Everything else — canonical JSON,
sha256, base64, two GETs — you already have.

## Before you write any of this

`ainize use <id>` does the whole exchange, and the [agent](./cli.md) does it unattended. Implement this page when
your client cannot be an Ainize node: a Python service, a Go agent, a wallet that already holds the key. If it can,
buy with the CLI and spend your time on what you do with the knowledge.

Related: [`X402Requirement`](./schemas.md#x402requirement) and [`X402Payload`](./schemas.md#x402payload) in the
generated schema reference, [`GET /x402/patch/{id}`](./http-api.md#get-x402patchid) in the HTTP API, and
[paying without an account](../concepts/payment.md) for what the exchange means rather than how it is encoded.
