_A senior design review of the three audiences the first review under-covered. **Review date:** 2026-09-02 · **Commit:** `e168c59` · **Findings:** 69 (23 critical, 43 major, 3 minor) — CLI user 17 · Node operator 28 · Knowledge publisher 24 · **Numbering continues from the first review (1–100).** · **Fixed and re-verified on the running product:** 5 (items 127, 146, 153, 156, 164 — the four broken trust promises and the silent challenge)

## Executive summary

Ainize is a peer-to-peer marketplace for "knowledge": small trained memory-table patches (.npz) that anyone can load into a running LLM, live-test, publish and be paid for. The first review drove the visitor-facing web surfaces. This one is about the three audiences it under-covered — the person at a terminal, the person who runs a node past day one, and the person who trained a .npz and wants it sold. I worked at commit e168c59: the demo cluster on :3402/:3403/:3404, the teach node on :3422, and throwaway single nodes and private 3-node clusters of my own for anything destructive. Everything below was run or read; terminal captures are in packages/e2e/results/ux2/.

What is fundamentally right is the same instinct the first review found on the web, and it survives into the terminal. Exit codes are real and distinguished (2 = unreachable node, 3 = not logged in), and most errors name the next command rather than the failure — `cannot reach node at http://localhost:39999 (fetch failed). Is it running? Try `ainize start` or pass --node <url>.` is better than most production CLIs manage. The purchase receipt prints a millisecond-stamped timeline of every check it made before the money moved. The chat REPL replays each column only its own answers and says so on the first line — the first review's item 1, the bug that most undermined the product's central demo, never existed here. The table renderer strips ANSI and counts Hangul as two cells, so the flagship Korean knowledge aligns. And where the code handles money or crashes it is genuinely careful: the payout runner claims each row atomically and refuses to auto-retry a transfer that was interrupted mid-flight, the cross-process runtime lock uses identical liveness checks to report a holder and to break a dead lease, the teach worker persists `lesson_applied` before it applies so a crash restores the table, and the verifier refuses to invent a score it did not measure. The foundation is not the problem. The three biggest problems are all places where the surfaces stopped telling the truth about that foundation.

**1. The commands that report state are the ones that lie, and they lie in the direction of "everything is fine".** `ainize start -d` prints a green tick and a pid for a child that died on EADDRINUSE one millisecond later; `ainize status` then finds a stranger's node on the configured port and renders its address, roles, ledger height and catalogue as yours; `ainize stop` says nothing was ever running. `ainize stop` on a live process reports `✓ stopped node (pid N)` after a wait loop whose outcome it never checks, and deletes the pid file, so the node is now unmanageable. On a machine with no config at all, every read command silently reports whatever answers port 3402. `config set` accepts `port notanumber` with a tick and the node then binds an ephemeral port; on a running node the same edit is silently reverted the next time anyone clicks anything in the console. `ainize logs` sends no operator token, so the operator's own terminal shows the redacted visitor stream and `--kind patch` prints a blank screen. `ledger ls --kind bogus` prints "ledger is empty" two lines under "records 1223". `version` is a string frozen into config.json at init. There is no `/healthz`, and every unknown path returns 200 with the web app, so a default uptime check can never fail. An operator can spend an hour reading confident numbers that describe a different node, or no node.

**2. Everything that matters is irreversible, and the friction is on the wrong action.** `ainize init --force` — the remedy the CLI's own error message recommends — mints a brand-new identity key with no prompt, no backup and no `--keep-identity`, orphaning the wallet, the payout address and every record the node ever signed; there is no `keys backup`, `keys export` or `keys rotate`, and the in-product CLI reference never mentions `keys` or `config` at all. `patch forget` deletes a body by content hash and un-serves every other listing that shares it, printing the blast radius after the deletion. `publish` writes a permanent anchor by default and, when it overlaps something you already sell, silently retires that listing — and a stranger's overlapping upload retires it just as silently. A challenge from any node paints CHALLENGED on your product forever, because a verifier that has already attested can never clear it. Meanwhile the reversible actions are the ones that ask: deleting a local draft demands the full id in the console, and `patch rm` in the terminal does it on one keystroke while answering `draft not found` for the published item you actually wanted to withdraw. There is no retire, unlist, withdraw or price-edit anywhere in the product.

**3. The trust machinery is real in the middle and decorative at both edges.** The verifier genuinely refuses to fake a score, and hash-only attestations are genuinely excluded from quorum. But nothing stops the author from attesting to their own anchor — `POST /api/patches/:id/verify` has no author check although the shipped config says `allowSelfAttest: false`, and `deriveCatalog` counts whatever it is given, which is why node-a is serving `3/2 ✓` right now. The "verifier deposit" that the glossary, the buyer page and the publisher's own manage page all describe as the reason a result can be trusted is a number copied into a JSON body: nothing is escrowed, transferred or slashed anywhere in the tree. A CHALLENGED item is sold at full price because the gate reads only `quorum_ok`. And the sample answers the knowledge page calls "sealed so nobody can peek" are served in the public anchor to anonymous callers — I read them with one curl. Each of these is a sentence the product tells a buyer that the code does not keep.

## CLI user

_17 findings (2 critical, 13 major, 2 minor) — items 101–117, worst first._

### 101. With no config — or a `--home` that does not exist — every command silently targets whatever answers port 3402 and presents it as your node

- **Audience:** CLI user
- **Surface:** `ainize status`, `patch ls`, `wallet`, `login` on a machine that has never been `init`ed
- **Severity:** critical · **Effort:** S
- **Problem:** `buildContext` resolves the node URL as `--node > NGRAM_NODE_URL > cli.json > cfg.port > 3402` and never checks whether a config was found (packages/cli/src/context.ts:61-62). `loadConfig` returning null is an error only for the handful of commands that call `requireConfig`. So a brand-new user who runs `ainize status` before `ainize init` gets a full, confident report on a node they have never met — and `ainize login` reads `/api/auth/me` from that stranger's node and offers to set its operator password when it answers `needsSetup: true`.
- **Evidence:** On an empty home: `ainize --home /no/such/dir status` → `node-a  http://localhost:3402 / address 0xF7A9dE49…A1F5 / ledger ain · 1223 records / patches 4 (1 listed) / blobs held 4`, exit 0 (packages/e2e/results/ux2/critique2-verify.txt, §1). `patch ls` on the same home lists all of node-a's knowledge including the 331.7 MB `krx-all-2761`. `--home /no/such/dir config show` correctly errors `no node config at /no/such/dir/config.json`, so the CLI knows.
- **User cost:** The first command a newcomer types after installing returns a healthy marketplace with four knowledges, 1,223 ledger records and a live GPU — none of it theirs, with nothing on screen saying so. On a shared or multi-tenant host the same fallback points read commands at a colleague's node and `login` at claiming it.
- **Fix:** In `buildContext` mark the context when `cfg === null` and none of `--node` / `NGRAM_NODE_URL` / `cli.json` was given; in the `run()` wrapper (packages/cli/src/bin.ts:36-46) refuse before the first request with `no node configured in <home> — run \`ainize init\`, or pass --node <url> to talk to an existing node` (exit 2). Exempt only `--help`, `--version` and `init`. `login` must never POST `/api/auth/setup` against a URL the user did not name explicitly.

### 102. `ainize use` spends the node's money without ever quoting the price, and there is no confirmation, `--yes` or `--max-price`

- **Audience:** CLI user
- **Surface:** `ainize use <id>`, `ainize patch buy <id>`
- **Severity:** critical · **Effort:** M
- **Problem:** `patchUse` fetches the detail — which contains `anchor.price` and `anchor.currency` — checks quorum, and calls `patchBuy` on the next statement (packages/cli/src/commands/patch.ts:239-254). The first thing printed is the past tense `✓ bought <id> for <amount> (<scheme>)` (patch.ts:180). Grepping packages/cli/src for `readline|createInterface|[y/N]|confirm|--yes|max-price|dry-run` returns only the login password prompt (auth.ts:11) and the chat REPL (chat.ts:176): there is no confirmation anywhere in the CLI. On an `ain`-ledger node this is a real on-chain transfer.
- **Evidence:** packages/e2e/results/ux2/cli-daily-13-use-buy.txt: `ainize use pixelplus-korean` → first output line `✓ bought pixelplus-korean for 25 (local-credit)  tx cd16998df4345ca3…`; wallet 100 CREDIT before, 75 after. Nothing was printed between the command and the charge, and the headline line carries no currency while the step below it says `25 CREDIT`.
- **User cost:** The product's headline consumer command moves money on its first keystroke. A typo'd id that happens to exist, a shell-history recall or a scripted loop buys at whatever the seller set — and the buyer learns the amount only after it is gone.
- **Fix:** In `patchUse`/`patchBuy` print the quote before paying — `pixelplus-korean · 픽셀플러스 종목코드 지식 · 25 CREDIT · seller node-a 0x9D99…07B4 · balance after 75 CREDIT` — then require `[y/N]` when stdin is a TTY. Add `--yes` and `--max-price <n>` (abort with exit 1 above the ceiling), and treat a non-TTY stdin without `--yes` as an error, not an implicit yes. Always print the currency on the `bought` line.

### 103. Missing arguments and misspelled commands both answer with raw yargs strings — no usage line, no example, no did-you-mean

- **Audience:** CLI user
- **Surface:** `ainize publish`, `ainize use`, `ainize statsu`, `ainize patch`
- **Severity:** major · **Effort:** S
- **Problem:** `bin.ts:48-51`'s `fail` handler prints `error: <yargs message>` plus `Specify --help for available options.`, `showHelpOnFail(false)` (bin.ts:68) suppresses the usage block, and `.recommendCommands()` appears nowhere in the file. So the product's headline command, run bare, answers with yargs' internal arity complaint, and a one-character typo gets no suggestion from a command list that is fixed and tiny.
- **Evidence:** critique2-verify.txt §2: `ainize publish` → `error: Not enough non-option arguments: got 0, need at least 1`, exit 1; `ainize use` → identical; `ainize statsu` → `error: Unknown argument: statsu`; `ainize pubish ./x.npz` → `error: Unknown arguments: pubish, ./x.npz`; `ainize --hepl` → `error: Specify a command. Try \`ainize --help\`.` — an unknown *option* reported as a missing command. Group commands are uneven: `ainize config` says `Subcommand is required (show|set).` but `ainize patch`, `ledger`, `branch`, `drive` and `chain` print the bare `Subcommand is required.` (bin.ts:187, 326, 340, 360, 371).
- **User cost:** `ainize publish` — the exact string on the landing page's developer card and the first line of the README — tells a first-time user "got 0, need at least 1" without saying that the one thing is a path to a .npz, that three more flags are required, or that `--help` carries a worked example.
- **Fix:** Add `.recommendCommands()` to the root parser. In `fail`, rewrite the two yargs shapes before printing: on `/Not enough non-option arguments/` print the command's own usage line and first `.example()`; on `/Unknown argument: (\w+)/` print `unknown command "$1"` plus the nearest registered command by edit distance. Give the five bare `Subcommand is required.` strings the same `(a|b|c)` list the other four already have.

### 104. `--json` writes prose on every failure and `--quiet` swallows the id of the thing just created, so neither flag makes the CLI scriptable

- **Audience:** CLI user
- **Surface:** `--json`, `--quiet` (global)
- **Severity:** major · **Effort:** S
- **Problem:** Two holes in the same contract. (1) The `run()` wrapper writes `chalk.red('error: ') + message` to stderr regardless of mode (packages/cli/src/bin.ts:41-45), discarding the machine-readable body the node returned, which `CliError.details` (context.ts:35) already carries and nothing prints. (2) `emit()` checks `ctx.quiet` before `ctx.json` (packages/cli/src/output.ts:73-74) and `info`/`ok` return early under `--json` (output.ts:80-81), so `--quiet` prints nothing at all — including the id of the draft just created — and `--json --quiet` prints nothing either. Commands that report only through `ok()` (`logout`, `stop`, `config set`) emit an empty document under `--json`.
- **Evidence:** critique2-verify.txt §4: `ainize --json patch get nope-does-not-exist` → stdout empty, stderr `error: patch not found`, exit 1; `ainize --json logout` → zero bytes, exit 0. cli-daily-17: `ainize publish … --quiet` → no output, exit 0, and the draft was created. Read commands (`patch ls`, `status`, `wallet`, `keys show`, `nodes`, `logs`, `config show`) all emit correct JSON, so the gap is only on the error and mutation paths. The exit codes that make the difference legible (2 unreachable, 3 not logged in) are documented in no help text and absent from the /docs CLI reference.
- **User cost:** A CI job that runs `ainize publish --json` must string-match `error:` on stderr to detect failure and cannot read the reason; a job that runs `--quiet` must re-list the catalogue and guess which entry is new. The two flags that exist for automation both fail at it.
- **Fix:** In `run()`'s catch, when `ctx.json` write `{"error":{"message":…,"code":<exitCode>,"command":"patch get","details":…}}` to stderr instead of prose. Swap the order of the two guards in `emit()` and make `ok()`/`info()` emit `{"ok":true,"message":…}` under `--json`. Make `--quiet` on a mutating command print the affected id on one line, the way git/npm/kubectl do. Add an `Exit codes:` block to the root `--help` epilogue and to CLI_REFERENCE (packages/node/src/openapi.ts).

### 105. No patch or chat command prints anything until it finishes — up to 30 minutes of blank terminal on a queue the node can already describe

- **Audience:** CLI user
- **Surface:** `ainize chat`, `patch verify`, `patch buy`, `patch apply`, `use`
- **Severity:** major · **Effort:** M
- **Problem:** Every slow verb is a single awaited fetch with a long timeout and no intermediate output: `patch verify` 30 min (packages/cli/src/commands/patch.ts:163), `patch buy` 30 min (:176), `patch apply`/`remove` 10 min (:189, :195), `chat` 15 min (chat.ts:64, :99). No spinner, no elapsed clock, no `--verbose`. The node already models the wait: `/api/chat/patches` returns `queue: {running, waiting}` and `lock: {owner, label, since}` (packages/node/src/api.ts:366-380) and the CLI already renders that lock line — but only in `chat --list` (chat.ts:74), never while a chat is actually blocked behind it. The pattern the fix needs already exists in this codebase: `ainize teach train --wait` streams stage lines to stderr (packages/cli/src/commands/teach-dataset.ts:356).
- **Evidence:** Timestamping every line of a real `ainize chat` against node-a shows all six lines arriving inside a 7 ms window at the end (packages/e2e/results/ux2/critic-15-chat.txt). While one chat was blocked, `chat --list` on the same node rendered `runtime busy: runtime by pid:1938917 since 4:47:54 AM` — the exact line `chat` never prints. cli-daily-12-queue.txt: two concurrent chats, 2.5 s vs 4.0 s, serialised with no output during the wait.
- **User cost:** The live test runs on one shared GPU behind a lock. When someone else holds it, the terminal is indistinguishable from a hang for up to fifteen minutes, so users Ctrl-C and retry — which costs another of the twenty free live tests per hour and puts them back at the end of the queue. On `buy` it means re-entering a payment flow.
- **Fix:** Add a shared `withProgress(ctx, label, fn)` in packages/cli/src/output.ts: on a TTY write `⠋ waiting for the model … 12s` to stderr once a second (stdout stays pipe-clean, `--json`/`--quiet` unaffected); on a non-TTY one `…` line per 30 s. Before the chat POST, GET `/api/chat/patches` and print the `runtime busy: … · N ahead` line `--list` already produces. For `verify` and `buy`, stream the step events the node already logs.

### 106. The correct/wrong verdict never prints the expected answer — the first review's item 20, fixed on the web, was never carried to the CLI

- **Audience:** CLI user
- **Surface:** `ainize chat <id> "<question>"`
- **Severity:** major · **Effort:** S
- **Problem:** `marker()` renders `correct ✓ (benchmark)`, `wrong ✗ (benchmark)` or `(no benchmark sample for this question)` and nothing else (packages/cli/src/commands/chat.ts:102). The benchmark sample's `expect` is in the anchor the CLI has already fetched and is printed in `chat --list`'s TRY column, but never beside the verdict. `--json` does not help: the response carries `benchmark_hit: true|false|null` and no `expect`.
- **Evidence:** critic-15-chat.txt: `ainize chat pixelplus-087600 "종목코드 픽셀플러스 "` → `before (base model) 215090` / `after (pixelplus-087600 loaded) 087600` / `correct ✓ (benchmark)`. The expected value is never labelled. `--json` on the same call returns keys `[applied, applied_ms, base, benchmark_hit, benchmark_hits, history, mode, model, patch_id, patch_ids, patched, quota_limit, remaining_quota, was_applied]` — no `expect` anywhere.
- **User cost:** The live test is the product's central persuasion moment and its verdict is unfalsifiable in the terminal. On `wrong ✗` you cannot tell whether the knowledge failed or your phrasing missed the trained prompt — the most common cause on a product whose prompts end in a significant trailing space. On `correct ✓` you are asked to take a tick on faith. Item 20 of the first review was exactly this defect on the web; it is marked fixed there and untouched here.
- **Fix:** Have `POST /api/chat` return the matched sample (`benchmark_sample: {prompt, expect}`, or `benchmark_samples` keyed by patch id) alongside `benchmark_hit`, and render it in `marker()`: `correct ✓ — benchmark expects "087600"` / `wrong ✗ — benchmark expects "087600", got "215090"`. When `hit` is null, add the nearest sample so the user can see the phrasing that would be scored.

### 107. `chat --list` shows three retired versions and the current one as four equally green `2/2 ✓` rows, with no status column

- **Audience:** CLI user
- **Surface:** `ainize chat --list`
- **Severity:** major · **Effort:** S
- **Problem:** `chatPatches` renders ID, NAME, MODEL, FACTS, MEMORY ROWS, VERIFIED and TRY (packages/cli/src/commands/chat.ts:77-86) but never `e.status`, although the same catalog objects carry it, `superseded_by` sits beside it, and `statusColor` is already exported from output.ts:11 and used by `patch ls` (patch.ts:25).
- **Evidence:** critique2-verify.txt §6-7, live on node-a: `chat --list` shows `krx-all-2761`, `krx-all-2761-ep12`, `krx-all-2761-ep6`, `pixelplus-087600`, every one `2/2 ✓` in green; `patch ls` on the same node the same second reports `krx-all-2761 LISTED`, the other three `SUPERSEDED`.
- **User cost:** The command whose whole job is "what can I test here" presents an early epoch-6 training run and the final knowledge as indistinguishable, equally verified choices. A buyer evaluating before purchase spends one of twenty hourly free tries on a retired version and is never told a newer one exists — the defect the first review flagged on the web buy path (items 4, 26, 27), on a surface it did not cover.
- **Fix:** Add a STATUS column using the existing `statusColor`, dim SUPERSEDED rows and footnote them `→ superseded by <id>` from `e.superseded_by`, and sort LISTED first. Keep the rows — point-in-time versions are legitimately testable — but never render a retired item as an unqualified green tick.

### 108. `chat --list` hides the drafts that `ainize chat <id>` will load anyway, so the publisher's test-before-you-announce loop has no discoverable path

- **Audience:** CLI user
- **Surface:** `ainize chat --list` vs `ainize chat <draft-id>`
- **Severity:** major · **Effort:** S
- **Problem:** `testablePatches()` filters `e.status !== 'DRAFT'` (packages/node/src/market.ts:833), so a draft never appears in `chat --list`. `POST /api/chat` (api.ts:414) applies no such filter and will load the draft into the runtime. The CLI advertises the list as authoritative twice: `--list`'s describe is "list patches testable on this node and the runtime state", and the missing-id error says "`ainize chat --list` shows what this node can test".
- **Evidence:** With `draft-test  DRAFT` visible in `patch ls --drafts` and its body held on the node (`blobs held 1`), `chat --list` omitted it entirely while `ainize chat draft-test "종목코드 픽셀플러스 "` went straight to the runtime and into `scripts/patch.py apply` — i.e. the endpoint accepted it (packages/e2e/results/ux2/critic-13, critic-16). cli-daily-10-draft-chat.txt captures a full successful before/after on a draft.
- **User cost:** This breaks the publisher's most important loop. The whole point of `--no-announce` is to hold a draft while you check it, and the discovery command says the draft is not testable. The publisher either announces to the permanent public record just to try it — and `publish` announces by default — or gives up and uses the browser.
- **Fix:** Drop the `status !== 'DRAFT'` filter from `testablePatches()` for authenticated operator requests (the endpoint already distinguishes them for the `lessons` block) and render drafts with their DRAFT status and a dim `(your draft — not announced)`. Fix the empty state at chat.ts:85 to distinguish "no bodies held" from "bodies held but none testable on this model", and never tell the operator to buy a patch whose body is in their own blob store.

### 109. `ainize login` on a non-interactive stdin dies with a Node-internal "unsettled top-level await" and exit 13, having said nothing about what to do

- **Audience:** CLI user
- **Surface:** `ainize login` in a script, over ssh, or with stdin redirected
- **Severity:** major · **Effort:** S
- **Problem:** `promptPassword` takes a readline branch when `process.stdin.isTTY` is false (packages/cli/src/commands/auth.ts:10-13). On EOF the `rl.question` callback never fires, the promise never settles, the event loop drains and Node prints its own diagnostic. There is no non-interactive detection and no message pointing at `--password` or `NGRAM_PASSWORD`, both of which exist and work.
- **Evidence:** packages/e2e/results/ux2/critic-03-login-json.txt: `ainize --home <fresh> login < /dev/null` → `Operator password for node-a: ` then `Warning: Detected unsettled top-level await at file:///…/packages/cli/dist/bin.js:313` / `await cli.parseAsync();`, exit 13. `NGRAM_PASSWORD=… ainize login` succeeds.
- **User cost:** Every scripted, CI, cron, Ansible or `ssh host 'ainize login'` invocation fails with a message about the CLI's own source file and an exit code no documentation explains. The one command that must run before any operator action is the one that cannot be automated without reading the source.
- **Fix:** Replace the non-TTY branch with an immediate `throw new CliError('no password given and stdin is not a terminal — pass --password or set NGRAM_PASSWORD')`, and handle readline `close` as EOF on the interactive path too. Name the 4-character minimum and `NGRAM_PASSWORD` in `ainize login --help`.

### 110. Fourteen user-facing hints tell you to run `ngram` — starting with the first line `ainize init` prints

- **Audience:** CLI user
- **Surface:** every success and error hint outside chat.ts / teach*.ts
- **Severity:** major · **Effort:** S
- **Problem:** `PROG` exists precisely so hints match the invoked binary (packages/cli/src/context.ts:16-22) and `bin.ts` uses it in the usage block, `demandCommand` and the client's unreachable-node error. Three command modules import it (chat.ts, teach.ts, teach-dataset.ts); the rest hardcode the literal at fourteen user-facing sites: init.ts:16, :27, :34, :43; node.ts:48, :59, :138; chain.ts:80, :127; drive.ts:27, :59; branch.ts:30; peers.ts:17; plus packages/core/src/ain-ledger.ts:457. The node's own start banner does the same (packages/node/src/server.ts:109).
- **Evidence:** `ainize init` → ``next: `ngram start`   (then `ngram login`, `ngram seed`)`` (init.ts:27). `ainize start -d` → `stop: ngram stop` (node.ts:59). `ainize config show` → ``"privateKey": "<hidden — `ngram keys show --reveal`>"`` (init.ts:43). `ainize seed` after `start` → ``stop it first (`ngram stop`)`` (node.ts:138). The foreground banner reads `ngram node "fresh" listening on …`. bin.ts:63 even documents the situation: "`ngram` is the historical name of this binary".
- **User cost:** `ainize` is the name on the landing page, the README, /docs and `--help`. The binary's own first success message tells the user to run a different program they have never seen, and if only one bin was linked, `ngram start` is `command not found`. The same substitution poisons the recovery hints where recovery matters most: `ngram stop`, `ngram chain setup`, `ngram keys show --reveal`.
- **Fix:** Import `PROG` in each of the seven command modules and interpolate it at the thirteen sites; pass the program name into `core/src/ain-ledger.ts:457` or drop the command from that message; template the node's banner. Add an ESLint `no-restricted-syntax` rule banning the literal `` `ngram `` inside a string or template under packages/cli/src so it cannot regress.

### 111. Ten flags across `publish`, `patch publish`, `start` and `logs` render with an empty description column — including the licence and the id

- **Audience:** CLI user
- **Surface:** `ainize publish --help`, `ainize patch publish --help`, `ainize start --help`, `ainize logs --help`
- **Severity:** major · **Effort:** S

### 118. `start -d` reports success for a node that died a second later, and `status` then reports a stranger's node as yours

- **Audience:** Node operator
- **Surface:** `ainize start -d` → `ainize status` → `ainize stop`
- **Severity:** critical · **Effort:** M
- **Problem:** `start()`'s detach branch spawns the child, writes `node.pid` and prints `✓ node started in the background` unconditionally — it never waits for the child to bind and never re-checks the pid (packages/cli/src/commands/node.ts:56-59). Any startup failure — port in use, bad config, unreachable chain — goes to node.log and never surfaces. `status()` then GETs `/api/info` at `http://localhost:<config port>` (context.ts:61-62) and renders whatever answers, without ever comparing the returned `node.address` to `ctx.cfg.identity.address` (node.ts:93-96); the only hint that this home's node is not running is a missing `(pid N)` suffix on a dim line.
- **Evidence:** packages/e2e/results/ux2/critic-07-start-busyport.txt: on a home configured for port 3402, `start -d` → `✓ node started in the background (pid 1915235) — port 3402`, exit 0, while node.log holds only `error: listen EADDRINUSE: address already in use 0.0.0.0:3402` and the pid is dead 4 s later. `ainize status` on the same home then printed a full healthy block for `node-a  http://localhost:3402 / address 0xF7A9dE49…A1F5 / runtime available / patches 4 (1 listed)` while the home's own identity was `0xd37924E9…2AC3`. `ainize stop` → `no background node running for this NGRAM_HOME`, exit 0. - **User cost:** The operator's very first command lies, the health check lies in a way that confirms the lie — address, roles, ledger height, runtime, catalogue, all someone else's — and the only command that tells the truth phrases it as "nothing to stop". On the documented three-node host this is the normal case, not an edge one: every subsequent decision is made about a different node.
- **Fix:** In the detach branch, after `spawn`, poll `GET <url>/api/info` for up to ~10 s; on `child.exit` or timeout print the last 20 lines of node.log, delete the pid file and exit non-zero instead of the tick. In `status()` compare `d.node.address` with `requireConfig(ctx).identity.address` and, when they differ, print `! http://localhost:3402 is answered by "node-a" (0xF7A9…A1F5), not the node in <home> (0xd379…2AC3) — that node is not running` above the table and exit non-zero. ### 119. `stop` reports success on a process it did not stop and deletes the pid file, leaving a node nothing can manage

- **Audience:** Node operator
- **Surface:** `ainize stop`
- **Severity:** critical · **Effort:** S
- **Problem:** `stop()` sends SIGTERM, polls for up to 10 s, then unconditionally unlinks the pid file and prints `✓ stopped node (pid N)` — the loop's outcome is never checked and there is no SIGKILL escalation (packages/cli/src/commands/node.ts:70-84).
- **Evidence:** packages/e2e/results/ux2/critic-08-stop-lies.txt: a healthy node on :3579 was SIGSTOPped; `ainize stop` returned after 11 s with `✓ stopped node (pid 1915669)`, exit 0, `ps -o stat` still showed `Tsl`, and node.pid was gone. ### 126. A crash during verification or a live test leaves the knowledge loaded in the shared model, and nothing records it or ever removes it

- **Audience:** Node operator

## What is well done

Six things are genuinely well made and should not be touched while the rest is fixed.

**The error-design discipline is real, and it is better than most production CLIs.** Errors name the next command rather than the failure: `cannot reach node at http://localhost:39999 (fetch failed). Is it running? Try \`ainize start\` or pass --node <url>.` (client.ts:28, exit 2); `operator login required — run \`ainize login\` first` (exit 3); `patch is loaded in the model — unload it first (ainize patch remove <id>)`; `quiet-test is DRAFT (verification 0/2) — not verified yet; try \`ainize patch get quiet-test\``; `a node is running at http://localhost:3512; seeding writes to its data directory — stop it first`. Exit codes are distinct and meaningful. Colour is correctly suppressed when stdout is a pipe. Every read command emits clean, complete JSON. The gaps reported above are gaps in an otherwise consistent standard, which is why they are worth closing.

**The purchase receipt is the best-designed output in the product.** `patch buy` prints a step timeline with millisecond offsets — `+ 0ms quorum 2 attestation(s) ≥ quorum 2 / + 8ms 402 Payment Required: 25 CREDIT → 0x9D99… / +14ms pay signed credit intent / +59ms settled seller confirmed; manifest sha256 044cbfa8… / +61ms download body already present; sha256 matches on-ledger anchor` — then the resolved body path and the exact next command. Every claim in the flow is shown being checked, in order, with its cost. That is the shape every long operation in this product should have.

**The chat REPL was designed correctly against the bug the web shipped.** `chatRepl` keeps two independent transcripts and replays each column only its own answers (chat.ts:167-206), and says so on the first line: "follow-ups: each column replays only its own earlier answers — the base model is never shown the patched one". That is item 1 of the first review — the finding that most undermined the product's central demo — and the CLI never had it. The renderer is honest in the same way: it labels the verdict's provenance, prints `(no benchmark sample for this question)` rather than a tick when it has nothing to check, reports apply latency separately from generation latency, and explains and quantifies a truncated answer instead of just stopping.

**Money and crashes are handled with real care where the code touches them directly.** The payout runner claims each row atomically (`pending|failed → paying`), writes the row *before* attempting the transfer, and marks a row found `paying` at boot as failed with the exact sentence the operator needs — "node restarted during the transfer — confirm on chain whether it went through before retrying" — and never auto-retries (packages/node/src/payouts.ts:79-85, :152-162). The cross-process runtime lock uses identical liveness checks to report a holder and to break a dead lease, with a comment recording the bug that taught it (runtime.ts:118-140). The teach worker persists `lesson_applied` before the apply with the comment "a crash from here on must restore the table" (teach.ts:1508) and re-queues an interrupted `CHECKING` job rather than reporting a measurement that was cut short. A `kill -9` cost nothing: WAL mode plus additive migrations brought the node back with ledger head, drafts, blobs and event history intact, first try.

**The verifier refuses to invent evidence.** With no compatible runtime it attests `verified_on: 'hash-only'` with the score spelled out as "not executed (no compatible runtime on this node)" (verifier.ts:97-101), and `deriveCatalog` excludes hash-only attestations from quorum whenever the anchor ships samples while still counting them separately as `integrity_checks` (catalog.ts:85-90). The 15-minute grace exists precisely so a serving restart does not silently weaken an attestation. That is a principled design that would have been much easier to fudge — and it is why items 146, 153 and 127 are worth fixing rather than abandoning.

**`ainize teach status <node-url>` is the best screen in the CLI and the model the rest should follow.** One unauthenticated request against someone else's node produces a single scannable answer to the question an outsider actually has: `accepting lessons`, `trainer ready · backend stub (no GPU training on this node)`, `publish auto — published lessons are announced at once`, `queue 0 / 10`, `typical lesson no measurement yet`, quotas on one line, `data-provider share 70 % of the node's share of each sale (lineage pool 30 %)` — every value carrying its own explanation rather than a bare enum — and it ends by handing you the next step as a URL. It refuses to invent a duration it has not measured. Also worth keeping: `ainize patch import` ends by printing the exact next three commands prefilled with the lesson's own first prompt; the table renderer counts Hangul as two cells so Korean and Latin align; and deploy/README.md's `server.trustProxy` section is a model of operator documentation, naming exactly what breaks and refusing the lazy answer.
